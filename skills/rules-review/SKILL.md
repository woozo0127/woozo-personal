# 개발 지침 리뷰

개발 지침 리뷰어 서브에이전트를 디스패치해 변경이 이 플러그인의 개발 지침을 지키는지 확인한다. 리뷰어에게는 세션 히스토리가 아니라 정밀하게 다듬은 컨텍스트만 전달한다.

이 스킬은 지침 준수만 본다. 버그, 보안, 계획 정합은 보지 않는다. 그런 리뷰가 필요하면 requesting-code-review를 쓴다.

## 언제 쓰는가

사용자가 지침 기준 리뷰를 명시적으로 요청할 때만 쓴다. 사용자가 요청하지 않았는데 requesting-code-review 대신 이 스킬을 쓰지 않는다. 지침 리뷰는 일반 코드 리뷰를 대신하지 못한다.

## 요청 방법

**1. 리뷰 범위를 정한다:**

사용자가 커밋 범위를 지정했으면 그 범위만 본다. `[HEAD]`에 끝 커밋 SHA를 넣는다.

지정하지 않았으면 시작 커밋부터 지금 워킹 트리까지 본다. 커밋된 변경과 아직 커밋하지 않은 변경이 함께 들어간다. `[HEAD]`에 `WORKTREE`를 넣는다. 시작 커밋은 세션을 시작할 때의 HEAD다. 그걸 알 수 없으면 다음을 쓴다.

```bash
BASE_SHA=$(git merge-base origin/main HEAD)
```

워킹 트리까지 볼 때는 미커밋 파일을 먼저 확인한다.

```bash
git status --porcelain
```

이번 세션에서 고치지 않은 파일이 있으면 리뷰 전에 사용자에게 목록을 보여 주고 포함할지 묻는다. git은 변경이 언제 생겼는지 모르므로 이 구분은 세션 기록으로만 할 수 있다. 빼기로 한 파일은 `[EXCLUDED_PATHS]`에 넣는다.

**2. 지침 파일 경로를 정한다:**

이 스킬 디렉토리에서 두 단계 위의 `rules/development.md`를 절대 경로로 만든다. 그 파일이 없으면 `${CLAUDE_PLUGIN_ROOT}/rules/development.md`를 쓴다. 둘 다 없으면 멈추고 사용자에게 알린다.

리뷰 대상 리포의 `rules/` 디렉토리는 쓰지 않는다. 같은 이름의 다른 파일일 수 있다.

**3. 리뷰어 서브에이전트를 디스패치한다:**

`general-purpose` 서브에이전트에 이 디렉토리의 `rules-reviewer.md` 템플릿을 채워 디스패치한다.

**플레이스홀더:**
- `[DESCRIPTION]` — 무엇을 만들었는지 간단한 요약
- `[PLAN_OR_REQUIREMENTS]` — 무엇을 해야 하는지 (계획 파일 경로, 태스크 내용, 또는 요구사항)
- `[BASE_SHA]` — 시작 커밋
- `[HEAD]` — 끝 커밋 SHA, 또는 워킹 트리까지 볼 때 `WORKTREE`
- `[EXCLUDED_PATHS]` — 리뷰에서 뺄 파일 목록, 없으면 "없음"
- `[RULES_PATH]` — 2단계에서 정한 지침 파일의 절대 경로

**4. 피드백을 반영한다:**
- Critical 이슈는 즉시 수정한다
- Important 이슈는 다음 단계로 넘어가기 전에 수정한다
- Minor 이슈는 나중을 위해 기록한다
- 확인 질문은 항목마다 답한다. 확인된 선택이면 근거를 남기고, 아니면 고치거나 사용자에게 묻는다
- 기존 코드 언급은 사용자에게 전달만 한다. 이번 변경에서 고치지 않는다
- 리뷰어가 틀렸으면 지침 원문을 들어 반박한다

템플릿: 이 디렉토리의 `rules-reviewer.md`
